# PET migration status

Reference PET commit: `e65fb1058411c8dad7ca70a09d501e0b18075e75` (upstream `main`, 2026-09-21,
"Restructure PIPT and POPT around explicit schemes, analyses and optimizers"). Paths are
relative to PET's `src/`.

**Sources:** port from upstream PET first. The exception is **GIES**, which is dormant upstream. It is ported from the GIES author's PET implementation (X. Luo (2021), Novel iterative ensemble smoothers derived from a class of generalized cost functions, *Computational Geosciences* 25(3), 1159–1189, [doi:10.1007/s10596-021-10046-1](https://doi.org/10.1007/s10596-021-10046-1)), which uses PET's old layout; its paths are relative to that implementation's root.

Status values:

- `not started`
- `in progress`
- `parity` (parity tests pass)
- `diverges` (an intentional difference, explained in Notes)

The Notes record the PET bugs found while porting, and how APEX treats each.

### Damping schemes

GIES's rule (`damping_schemes["rlmmac"]`, `DampingSchedule`) and PET's LM rule (`damping_schemes["lm"]`, `LMDampingSchedule`) are each method's default, and are pinned by the GIES and LM-EnRML parity cases above. Either method may run the other's scheme (`[method.damping]`). These are APEX combinations, tested in `tests/workflows/test_damping_schemes.py`: every trial's λ is recomputed from the run's history by the scheme's rule.

### Method × strategy pairs (APEX combinations)

PET's parity tests pin one strategy per method. Every other pair of an iterative method (`gies`, `lm_enrml`, `gn_enrml`) and a strategy is an APEX combination, tested against independent references in `tests/workflows/test_method_strategy_pairs.py`. On the linear-Gaussian case:
- `approx` and `rlmmac` reach the least-squares fit;
- `full` and `subspace2` reach the RML solution;
- `subspace` reaches Evensen et al.'s closed form with `(1 + λ) E Eᵀ`;
- `margis` reaches the RML solution with `C_d / w`, its marginalised error scale;
- the localized strategies reach the least-squares data mismatch within 0.2 %;
- on the tanh case every pair reaches 30–34 % of the prior's data mismatch.

**Deliberate differences from upstream:**
- **Coordinates:** APEX positions are 1-based Eclipse `(i, j, k)`, with `grid = [nx, ny, nz]` and the state in Eclipse order. PET's are 0-based along its `field = [nz, nx, ny]`, flattened in C order. So the two flatten alike when PET's `x` is Eclipse `j` and its `y` is `i`, and the anisotropy's first axis (PET's `x`) is `j`, as in APEX's `distance`.
- **Evaluation:** the kernel is evaluated at each cell's offset instead of from PET's cropped `2·nx × 2·ny` stencil. The values are the same (2e-15), including for a radius beyond the grid on both axes, except where PET's crop is asymmetric (below).
- **Anisotropy:** the ratio divides the rotated offset's first component, along Eclipse `j` (PET's `x`), so a ratio of 2 doubles the reach along `j`. This is PET's code; its docstring says the ratio compresses the kernel to half its width.
- **Checkpoint:** the taper itself is checkpointed, so a resume does not re-read `taper_file`.
- **File layouts:** a `taper_file` or `actnum_file` must be flat in Eclipse order or shaped `(nx, ny, nz)`; other shapes are refused, because a same-size array in another layout would be read in the wrong cell order. An `.npz` `actnum_file` is read from its `actnum` array, as in PET.
- **Radius:** a float; PET truncates it with `int()`.
- **Furrer–Bengtsson:** uses the actual ensemble size; PET uses the one it is built with, 50 if none is given.
- **Names that do not exist:** an entry naming a data type, a time or a variable that does not exist is an error; PET ignores it, so a misspelt name drops data silently. Data that no entry localizes are logged.
- **Not supported:** pickled entry files and CSV rows. They belong to the importer.

**Upstream defects found (not reproduced):**
- **The kernel is off centre by one cell where the stencil crop is asymmetric.** The stencil's coordinates run over `[−n, n − 1]`. A rotated, elongated kernel whose support reaches past the stencil on one side keeps column `−n` with no mirror `+n`, so `_crop_kernel` trims it asymmetrically and `_place_kernel`'s `pos − k//2` misplaces it by a cell. The case `distance_entries_miscentred` (12 × 26, radius 14, ratio 0.5, 45°) shows PET's taper equal to APEX's centred one cell lower in `j` (up to 0.12 apart). A random test found 535 such cases in 20,000 (up to 1.0), mostly on thin grids, and 9 in 3,000 on grids of 10–60 cells per side (0.05–0.15). APEX centres the kernel.
- **The `import` kernel cannot run.** `_parse_rows` builds its entry with `positions = None`, and `_resolve_mask` iterates `entry.positions` for every kernel: `TypeError: 'NoneType' object is not iterable`. APEX's `import` entry uses its file (`taper_file`, one value per cell in Eclipse order) as the taper.
- **With `emp_cov`** the distance branch multiplies the anomalies by `√(N − 1)` (recorded under approx above), so the localized `emp_cov` step is not compared.

**GIES implementation defects found porting ES-MDA's localization:**
- **`autoadaloc` in `approx_update` adds the taper to the state.** It assigns `auto_ada_loc`'s `(step, tapering matrix)` tuple to `self.step`, so `aug_state + self.step` broadcasts both (`(2, n_state, N)`); the GIES implementation's localized ES-MDA cannot run. Its RLM-MAC branch unpacks the tuple. The reference stores the intended step (the first element).
- **The `INI_ONLY` taper drops a member for ES-MDA.** `loop/assimilation.py` builds it from `pred_data[:, :-1]`, assuming the last column is GIES's mean-model forecast; for other schemes it is a real member.

**Localization notes: deliberate differences from the GIES implementation:**
- **Distance in 3-D.** The GIES implementation's `dist_loc` returns one layer only. APEX tapers each layer from that well's completions in the same layer, with no vertical distance, so layers without a completion are not updated by the well's data. This is an APEX extension, not a port; a vertical-distance option can be added.
- **Blocks.** Per-variable thresholds use the state layout's variable sizes. The GIES implementation uses `prod(FIELD)` (or `prior_info[p]['active']`) for every parameter. The two agree when every variable is one full field. The parity cases have one block, so the multi-block case is covered by unit tests only.
- **Correlation floor.** Standard deviations are floored at an absolute 1e-6 in physical units, as in the GIES implementation. Rows with a tiny but nonzero spread therefore get correlations shrunk by std/1e-6.
- **Unmatched data.** Data whose well has no positions raise an error by default. The GIES implementation zeroes them silently; `unlisted = "zero"` opts in to that behaviour.

**Localization notes: GIES implementation defects found (not reproduced):**
- **Shuffle is not a permutation.** `auto_ada_loc` builds the shuffled ensemble with a derangement fix-up. With exactly one fixed point it overwrites instead of swapping (`rp[u] = pick; rp[pick] = u`), which *always* duplicates the member `pick` and drops the old `rp[pick]` (e.g. `[2, 1, 0]` → `[2, 2, 1]`). APEX swaps. Parity cases inject derangements, where both agree.
- **`ini_only` step scaling.** The branch applies the taper to a gain built from state anomalies *divided by the state scaling* and never multiplies back. The scaling is `sqrt(prior_info variance)` (`calc_scaling`, active when `SCALING` is on, which is PET's default), not the ensemble std. So the step is off by that factor unless every prior variance is 1. APEX uses the unscaled anomalies. The parity test pins its behaviour.
- **Distance stencils crash near some edges.** `_repos_mask` builds the wrong shape (e.g. (7, 12) for an (8, 12) grid) for some anisotropic stencils at a corner, and raises. APEX evaluates distances directly.
- **Distance masks are single-layer.** `dist_loc` returns one layer (`int(z_range)`), so it only fits 2-D fields or one parameter per layer. APEX tapers each layer from the completions in that layer.
- **The sigmoid taper ignores the threshold.** It is `expit(50 (|ρ| − (1 − nstd)))`, which uses `nstd` directly as a correlation level. APEX reproduces it and documents it.
- **Failed reads become zeros.** `eclipse.extract_data` wraps summary reading in a bare `except: pass`, so a failed read gives all-zero predictions without warning, and GIES then "converges" on them.
- **The `.pipt` parser drops the last keyword** unless a blank line follows it. That can drop `STARTDATE`, which gives the zero predictions above.
- **The GIES `dist_loc` step stops with a shape error.** `rlmmac_update.py` computes `real_obs_data - aug_pred_data` with shapes (n_d, N) and (n_d, N+1), because GIES appends the mean-model column, and raises a broadcast error. The `localanalysis` branch and the unlocalized `emp_cov` path have the same bug.
- **The soft taper reverses when the cutoff reaches 1.** `rational_function(1 - |ρ|, 1 - cutoff)` takes `|1 - cutoff|`, so for cutoff > 1 the taper *grows* with the noise level; for example, a cutoff of 2.5 keeps half of a zero correlation. The cutoff `nstd · sqrt(2 ln n) · σ` exceeds 1 for small ensembles and large blocks (about 1.05 for N = 25 and 10⁶ cells). There, the hard taper also zeroes the whole column. APEX treats a column whose cutoff is ≥ 1 as having no significant correlation (taper 0 for every taper type) and logs a warning.

**PET defects in its prior sampler.** `apex pet-import` reproduces them where that is exact (`--pet-geometry`, the default) and notes it; `--intended-geometry` samples what the keywords describe instead (`minor_range = range`, `major_range = aniso · range`, `azimuth = −angle`, since PET's angle is clockwise).

**`apex pet-import` of `compress`** (`storage/pet_compress.py`). PET numbers vintages by walking the data table row by row, then column by column: each non-empty cell of a `compress_data` type takes the next `mask` file and `min_noise` entry, and cells beyond the masks stay uncompressed. The importer repeats that walk and writes one `wavelet` transform per data type, mask and `min_noise`, with the vintages' `times`. Keyword mapping:
- `dim` → `grid`, `wname` → `wavelet`; `level`, `order` (always written; APEX's default is `F`, the Eclipse cell order), `threshold_rule`, `min_noise` and `inactive_value` keep their names;
- `mask` → `mask_file` (copied to `masks/`, flattened as PET applies it, D2; a missing file means all active, as in PET, with a note);
- `colored_noise` → `noise = "coloured" | "white"`; `th_mult` → `threshold_multiplier`; `use_hard_th` → `thresholding = "hard" | "soft"` (PET's default is soft); `keep_ca` → `keep_approximation`;
- `bayesian` with white noise → `universal` (what PET computes, D4, noted); soft thresholding is noted, since APEX also shrinks the predictions (D1);
- `use_ensemble` is refused (as PET refuses it), and so are unknown keys, negative `th_mult`, missing `min_noise` entries, and scalar cells of a compressed type.

Field cells (`.npz`) are copied to `fields/` as `[[observations.fields]]`. An uncompressed field needs an `['abs', v]` variance; a compressed field's variance cell is replaced by the noise estimate, as in PET.

**PET with pandas ≥ 3.** PET does not pin pandas. With pandas 3, `.npz` cells in a CSV data file fail: `read_csv` makes a string column, and PET cannot store the loaded field in it (`TypeError: Invalid value for dtype 'str'`). CSV index labels are also parsed as dates (`parse_dates=True`), so integer labels break. PET's own test uses pickled object-dtype frames, and so does the `pet_import_compress` generator.

**PET defects in its wavelet compression:**
- **D1: soft thresholding biases the observations.** The observed coefficients are shrunk by their thresholds, but the predicted ones are not (`compress` without `th_mult` skips thresholding), so every retained observed coefficient is biased toward zero by `t` relative to the predictions. PET's default is soft (`use_hard_th` unset). APEX intentionally diverges: it shrinks the predicted coefficients by the same observed thresholds, so both go through one operator, and defaults to hard thresholding. The parity test checks that APEX's soft output is PET's prediction shrunk.
- **D2: mask flattened in the wrong order.** `organize_sparse_representation` flattens the mask in C order, but `compress` reshapes the data with `order` (`'F'` in PET's own test). With a non-trivial mask and `order = 'F'` data land in the wrong cells. APEX flattens the mask in `order`; the masked parity case uses C order, where the two agree.
- **D3: Bayesian threshold.** PET computes `s_y = ‖c‖₂ / n` (the RMS is `‖c‖₂ / √n`) and uses `|s_y² − σ²|` where BayesShrink (Chang, Yu & Vetterli 2000) uses `max(s_y² − σ², 0)`. Reproduced as PET computes it, so thresholds under this rule are off by roughly a factor √n from BayesShrink's.
- **D4: rule silently ignored with white noise.** With `colored_noise = no` PET always uses the universal rule, whatever `threshold_rule` says. APEX refuses `bayesian` with white noise.
- **D5: missing mask files.** A mask path that does not exist silently becomes an all-true mask, and PET writes it to `mask_<k>.npz` (k counted from 1) in its working directory. A later entry of that name is then read all-true, and the original file is overwritten. APEX's `mask_file` must exist; no mask means all cells active. `apex pet-import` reproduces both effects, with notes.
- **D6: noise and data lengths can differ.** PET counts `est_noise` from its threshold mask (`|c| ≥ t`) but selects data by non-zero coefficients, so with `th_mult = 0` an exactly-zero coefficient (e.g. in a constant inactive region) is counted in the noise but not in the data, and the variance vector is longer than the data. APEX derives both from one selection (`|c| ≥ t` and `c ≠ 0`, as PET's data).
- **D7: `compress_data` as a string is a substring test.** The reader tests `column in compress_data`, so `compress_data = "avo"` also compresses columns `av` or `a`; the forecast (`_compressed_rows`) matches exactly. APEX matches exactly, and `apex pet-import` refuses a string that contains another observed type's name (give a list).
- **D8: empty vintages.** When every coefficient is below its threshold, PET stores a vintage with no data, silently. APEX refuses it ("no wavelet coefficient survives the thresholding").
- **Stricter than PET in `apex pet-import`:** scalar cells of a compressed type within the masks (PET would broadcast them into a constant field), fields containing NaN (PET would skip them when numbering vintages, shifting later masks), masks that are not 0/1, flags other than yes/no/booleans, and a `threshold_rule` other than `universal`/`bayesian` with coloured noise (PET raises too, case-sensitively). With white noise any rule becomes `universal`, as PET computes.
- **Caveat (not a bug): non-orthogonal wavelets with white noise.** One noise level for every band holds only for orthogonal transforms; for biorthogonal wavelets (e.g. `bior2.2`) PET's white-noise variances are mis-stated. APEX warns and suggests `noise = "coloured"`.
- **Caveat (not a bug): the `min_noise` floor.** A band with no measurable noise (a constant inactive region, noise-free synthetic data) gets variance `min_noise²` (1e-18 by default), which forces an almost exact fit of its coefficients. APEX warns, naming the bands.
- **Caveat (not a bug): noise estimates with long wavelets.** Symmetric extension adds boundary coefficients that carry less noise, so the MAD estimate is biased low for wavelets longer than haar (about 5% for db4 on a 128×128 grid; measured). Haar is unbiased.

**Differences from the original MATLAB implementation of the wavelet compression (unpublished).** Checked against a line-by-line Python transcription; MATLAB itself was not run. The fields were 3-D, on even and odd grids, with db2 at level 3 (MATLAB's defaults) and `keep_cA` on and off.

In 6 of 7 cases APEX keeps exactly the same coefficients and gives identical compressed observed and simulated data. The following agree: the transform (PyWavelets `symmetric` is MATLAB's default `sym` extension), the noise estimate from the finest diagonal band, the universal threshold `mult·√(2 ln n)·σ` with hard thresholding, thresholding of the approximation band unless kept, reusing the observed data's retained indices for simulated data, and one noise standard deviation σ for every retained coefficient. MATLAB's `W` is a standard deviation in that workflow: the data mismatch divides by `W.^2`. APEX keeps its code as is by design. The differences:

- **The noise estimator.** MATLAB uses `median(|c|)/0.6745` (Donoho & Johnstone's). APEX, like PET, uses the median absolute deviation about the median, `median(|c − median(c)|)/0.6745`. σ differed by 0.04–0.5% in the tests, and the threshold by the same factor. With a large mean offset, 4 of 408 retained coefficients near the threshold changed.
- **Ties at the threshold.** MATLAB zeroes `|c| ≤ t`, and APEX (like PET) zeroes `|c| < t`. They differ only for a coefficient exactly at the threshold.
- **`n` in the universal threshold.** MATLAB uses the whole cube (`numel(input_trace)`); APEX uses the active cells, since its fields are given over them. The two are identical without a mask. With one, APEX's threshold is lower by `√(ln n_active / ln n_cells)`, e.g. 0.984 for 30% inactive cells in 100,000.
- **Defaults and extras.** MATLAB defaults to `db2`, level 3; APEX requires both. MATLAB has only white noise, the universal rule and hard thresholding. APEX adds coloured noise, the Bayesian rule, soft thresholding, masks, the `min_noise` floor, 1-D and 2-D grids, and the cell order.

## ES-MDA notes

**Differences from PET (intentional):**

- **Correlated `C_d` whitening (PET bug).** `misc/sampling.py::gen_real` returns the upper Cholesky factor `U` of `alpha C_d` (`alpha C_d = UᵀU`) and samples correctly as `Uᵀz`. `analysis/approx.py` then whitens with `solve(U, ·)`, i.e. `U⁻¹`, so its gain uses `UUᵀ` in place of `alpha C_d`. APEX uses `L = Uᵀ` for both sampling and whitening. On `esmda_approx_dense` the steps differ by 17%, and PET's output matches the `UUᵀ` formula to 8.8e-16. A diagonal `C_d` (1-D variances, the usual PET input) is unaffected. The same whitening is probably shared by other analyses; check when porting them. The subspace analysis shares it; there it cancels only when `S` spans the data space (`n_data < N`, untruncated), not in the usual regime (see its row).
- **Inflation sum rule.** PET asserts `sum(1/alpha) == 1` to machine epsilon, which rejects valid rounded schedules such as `[9.333333333, 7, 4, 2]`. APEX uses a relative tolerance of 1e-9.
- **State scaling** (`state_scaling`, the square root of `prior_info` variance per row) is omitted. It divides and multiplies back and cancels exactly when every prior variance is positive. With a zero prior variance, PET produces NaN (`inf * 0`) and APEX a finite step.
- **Input validation.** APEX rejects non-finite ensembles, naming the array (PET fails in the SVD or propagates NaN), and bounds with `lower > upper` (PET's clip would silently use the upper bound).

**Other PET observations (not reproduced):**

- `analysis/approx.py` reads `keys_da.get('emp_cov', False)` as a truth value, so a legacy `emp_cov = "no"` string would enable the empirical-covariance branch. The old code compared it with `== 'yes'`.
- `gen_real`'s diagonal shortcut, `np.count_nonzero(var - np.diagonal(var)) == 0`, subtracts the diagonal along rows. It never fires for a diagonal matrix, and can fire wrongly for, e.g., a constant matrix, where it would take an elementwise `sqrt`.
- `ESMDA.calc_analysis` computes `self.E = enObs @ proj`, which the approx analysis never reads.

## LM-EnRML notes

Ported from upstream PET `e65fb10` (Chen & Oliver, 2013). `LMEnRML` subclasses APEX's `GIES` and reuses its loop: trials from the last accepted iterate, failed members, checkpoints and bit-identical resume. It adds LM's damping rules through two hooks, `_initial_damping` and `_judge`, which leave GIES unchanged; GIES's golden outputs are bit-identical. What LM-EnRML does differently from GIES:
- no mean-model forecast;
- λ is divided by `lambda_factor` only when the data mismatch spread falls too;
- `lambda_max` stops the run;
- `max_inner_iter` rejections in a row stop the run. GIES's MATLAB mode raises the damping instead.

The data mismatch spread (population std over members, as PET's `np.std`) is recomputed from the saved forecasts, so the checkpoint holds nothing new.

**PET bug, not reproduced: a retried step uses the rejected trial's forecast.** PET's `calc_analysis` (`enrml.py:179`) takes `enY` from `pred_data`. Every forecast overwrites it (`forecast.py:48`), including a rejected trial's, and a rejection restores only the data mismatch. So PET's retry updates the last accepted state with the rejected trial's forecast: the innovations `d - g(m)` and the data anomalies do not belong to the state being updated. APEX retries from the accepted iterate and its own forecast, as Chen & Oliver's algorithm does, so APEX and PET runs diverge after the first rejection. The parity tests compare the step and the damping rules separately, which this does not affect.

**Localization:** LM-EnRML and GN-EnRML take upstream PET's localizations of the approx update, `adaptive_projected` (in the rank-`r` space, `projection = "rank-r"`) and `distance_entries` (`distance_loc`), and local analysis; the tapers ported from the GIES implementation (`adaptive`, `adaptive_per_update`, `distance`) are refused there. A native `[method.strategy] name = "approx"` without `energy` gets `ApproxUpdate`'s default of 0.98, not PET's LM default of 0.95. PET reads the truncation `energy` from the `iteration` block, where its default is 0.95. On the linear test case the posterior comes within about 7e-6 of the per-member least-squares fit: PET's rules hold λ at 0.008 there, so each step leaves a fraction `(1 + λ)/(1 + λ + s²)` of the remaining error.

## GIES notes

Source: the GIES author's implementation, because upstream's `gies/` is dormant. The GIES modules import only numpy and scipy.

**GMAC (not in PET).** `update_strategies["gmac"]` generalises RLM-MAC with composable metric terms; one identity l2² term is `rlmmac` bit for bit. It is validated against a transcription of the method author's MATLAB code: see [GMAC](gmac.md).

**Convergence on a worse trial (intentional difference).**
- The GIES implementation's `check_convergence` stops the run when a trial's mean data mismatch changes by less than `data_misfit_tol`, even when the trial is worse, and so rejected.
- On a SNESIM facies case this ended GIES with `adaptive_prior` after one rejected trial that had barely moved: its relative change was 6e-5.
- APEX's `DampingSchedule` now stops only on an improving trial. A worse one is rejected and the damping raised, as the author's MATLAB RLM-MAC does, which tests the reduction on accepted steps only.
- `converge_on_rejection = true` reproduces the GIES implementation's rule. The unit test that replays its `check_convergence` uses it.
- `max_stalled_rejections` (default 3) stops a run after that many such rejections in a row, so a stalled update does not spend the whole iteration budget.
- The same applies to PET's upstream rules: `lm` (LM-EnRML's `LMDampingSchedule`) and GN-EnRML's `GNStepSchedule` converge only on an improving trial (or at `lambda_max`), have `converge_on_rejection` (true in their parity tests, which replay PET's `score_and_commit`) and `max_stalled_rejections`. `lm` also has `confirm_convergence` (default true; false in its parity tests): above `lambda_min` a small improvement is accepted with λ relaxed, and two in a row stop the run. `rlmmac` has it too, false by default, so GIES's default rule is PET-fork's and the MATLAB RLM-MAC's: its damping starts at 1, relative to the data's singular values, and falls after each accepted step, so a small improvement is rarely a damped one.

**APEX addition: a separate damping reduction factor (intentional difference since 2026-10-13).** `DampingSchedule.reduction` multiplies λ after an accepted trial, instead of the GIES implementation's division by `factor`. It is the `lambda_reduction_factor` of the author's MATLAB RLM-MAC (with `lambda_increment_factor` as `factor`), and its default is 0.9 since 2026-10-13. `reduction = 0.5` with `factor = 2` is the GIES implementation's division, bit for bit; the parity tests of the step are unaffected, and those that replay its rule set `reduction = None`. `apex pet-import` writes `reduction = 1/lambda_factor` (0.5 at the default factor of 2), so an imported case keeps the GIES implementation's rule.

**The step equals the author's MATLAB RLM-MAC at the same λ (checked 2026-10-13).** There are two MATLAB versions. `RLM_average_cost.m` (2014) leaves both anomalies unscaled. `RLM_MAC.m` (2017) scales both `deltaD` and `deltaM` by `1/√(N−1)`, with `deltaD` taken about the mean model's forecast. Both give the same step, and it is APEX's default `rlmmac` (`scale_data_anomalies = true`). MATLAB's `alpha = λ·Σ Wd²/r` is APEX's γ = λ·mean(s²). In the unscaled version `Wd = √(N−1)·s`, and the `√(N−1)` of its `deltaM` cancels it, so a MATLAB λ carries over unchanged. `tests/unit/algorithms/test_da_rlmmac_matlab.py` checks this to 1e-9 against a line-by-line NumPy transcription of both versions (`tools/rlmmac_reference/`; MATLAB is not licensed on the host, so the cases are also stored as `.mat`). It also pins two things:
- APEX at `λ·(N−1)` is not MATLAB at λ: it is a more strongly damped step.
- The unscaled `rlmmac` (the GIES implementation's, which logs a warning that it does not follow the theory) is the MATLAB step times `1/√(N−1)`.

Among other things, these can make the runs differ. The first two are edge cases:
- MATLAB truncates where the cumulative energy is strictly above `tsvdData`, while APEX's `truncated_svd` truncates where it reaches the energy (differs only on ties).
- MATLAB floors `alpha` at 1e-3: that is 1e-3 in APEX's units for `RLM_MAC.m`, and 1e-3/(N−1) for `RLM_average_cost.m`. APEX has no floor (matters only for a collapsed ensemble).
- **Acceptance** (not an edge case). MATLAB judges a trial by `getDataMismatch` against the *unperturbed* measurements (`Σ (d − d_obs)²/W²`, averaged over the members). APEX, like PET, judges it by the data mismatch against each member's perturbed observations. The two can accept or reject different trials, and then the runs part. `RLM_MAC.m` also clips negative perturbed data to zero (line 86). Its line 85 sets perturbed data to zero where the measurement is zero, but with a linear index, so in the first member only. APEX does neither.
- **Edge cases of the loop.** APEX drops numerically null singular values, and MATLAB keeps them (this matters only at `tsvdData ≥ 1` with a rank-deficient `deltaD`). On an exact tie MATLAB accepts and APEX rejects. MATLAB's stopping rules are below.

**Also added: inner retries.** `GIES(max_trials_per_iteration = n)` retries a rejected trial inside the same iteration, from the same accepted iterate with the increased damping, as MATLAB's inner loop. MATLAB's `iterLambda` starts at 1, so `maxInnerIter = 5` allows `n = 4` trials. An accepted trial ends the iteration. When all `n` trials are rejected, λ is multiplied by `factor` once more, raised to at least the initial λ, and the iteration ends without an update, as in MATLAB. `max_iterations` then counts outer iterations, like `maxIter`. Every trial keeps its own number in the results. An exhausted iteration adds no record of its own, where MATLAB saves the unchanged ensemble again; its extra damping shows in the next trial's record, and a `trials_exhausted` event is logged. Unset (the default), every trial is an iteration, as in the GIES implementation, and the outputs are unchanged.

Not ported:
- **The minimum-reduction test** (APEX keeps the GIES implementation's test by design). MATLAB applies it to accepted steps only, and in percent: `minReduction = 1` is `data_mismatch_tolerance = 0.01`. APEX, like the GIES implementation, also stops on a rejected trial whose data mismatch changed by less than the tolerance. On an exact tie MATLAB accepts, while APEX stops without accepting.
- **The data mismatch threshold.** MATLAB also stops when the mean data mismatch falls below `beta²·p`. With `beta = 0`, this never triggers.

**Intentional differences from the GIES implementation:**

Notation: `s_pet` are the singular values of the GIES implementation's unscaled whitened data anomalies `S_d^-1 (g(x_j) - g(x_mean))`, and `s_apex = s_pet / sqrt(N-1)` those of APEX's scaled ones.

- **Data-anomaly scaling.** The GIES implementation divides the state anomalies by `sqrt(N-1)` (`proj`) but leaves the data anomalies unscaled. APEX scales both. With its localised branch's `gamma = lambda * mean(s^2)`, APEX's step is then `sqrt(N-1)` times the GIES implementation's at the same `lambda`, in every direction; no `lambda` maps one onto the other, since `lambda * k` divides APEX's heavily damped directions by `k` (`lambda * (N-1)` leaves them at `1/sqrt(N-1)` of the GIES implementation's) and leaves the weakly damped ones at `sqrt(N-1)` (on the Brugge MEC case, `lambda = 102` matched its first step, but its steps grew to `sqrt(102)` times the reference's as `lambda` fell). `rlmmac`'s option `scale_data_anomalies = false` (2026-10-12) leaves them unscaled for reproducing its runs: the localized steps then equal its own (`test_adaptive_localization_matches_pet_fork`, both settings).
- **Regularisation.** The GIES implementation's unlocalised branch uses `(lambda I + S^2)` (formerly `(lambda + 1) I`), while its localised branch uses `gamma = lambda * mean(s^2)`. APEX uses `gamma = lambda * mean(s_apex^2)` over the kept singular values. The meaning of `lambda` is strategy-specific: `ApproxUpdate`'s `1 + lambda` is absolute.
- **Truncation.** The GIES implementation keeps singular values whose cumulative fraction is `<= energy`. That can keep none, which gives a zero step. APEX uses `truncated_svd`: the first rank reaching `energy`, and at least 1. The two rules differ by one rank at any energy below 1, so parity is tested at `energy = 1`.
- **The combined effect is exact and tested.** With no truncation, `step_apex = sqrt(N-1) * step_pet` for `lambda_apex = lambda_pet / mean(s_pet^2)`, equivalently `lambda_pet / ((N-1) mean(s_apex^2))`. Measured to 1e-15 on both cases, this shows that the mean-model centring, whitening, innovations and state handling are otherwise identical. Perturbations are bit-identical, and the data mismatches match its `calc_objectivefun`.
- **Correlated `C_d`** has the same upper-Cholesky whitening issue as upstream ES-MDA (`solve(scale_data, ·)` at `gies_base.py:110`, `rlmmac_update.py:222`). `gies_rlmmac_dense` pins its output to the `lambda U U^T` formula; APEX uses `C_d`.

**Also different from the GIES implementation:**

- **Acceptance on convergence.** `DampingSchedule.decide` accepts a converged trial only if its data mismatch improved, as upstream `e65fb10` `IterativeEnRML` does. The GIES implementation's `check_convergence` returns `success = False` on convergence, but the loop still saves the trial (`assimilation.py:254-257`). So it keeps a worse converged trial, and also a trial rejected at `max_iter`.
- **Numerically null directions.** `RLMMACUpdate` drops singular values `<= eps * max(shape) * s_max`. Without this, at tiny damping `s / (s^2 + gamma) ~ 1/s` turns rounding noise into an O(1) step; this happens whenever `L^-1 dY` is rank-deficient, as for any linear model. APEX also raises if all data anomalies are zero, and requires `initial` damping > 0, since a zero damping can never recover after a rejection.

**Damping rule** (`gies_base.py::check_convergence`), shared by `DampingSchedule.decide`: stop when `|1 - data_mismatch/previous| < data_misfit_tol`. Otherwise accept an improvement and divide `lambda` by `lambda_factor` (unless `lambda <= lambda_min`), or reject and multiply. The GIES implementation reads `step_tol` but never uses it, and `lambda_max` only feeds the `why_stop['lambda_stop']` report flag, so neither is ported.

**Other GIES implementation observations (not reproduced):**
- **3-D variables are tapered only over one grid's worth of rows.** `ensemble.py` records a variable's `ACTIVE` size only for 2-D priors, so `auto_ada_loc` with `INI_ONLY` builds the taper of a variable declared with a 3-D `GRID` over `nx·ny·nz` rows and leaves its other rows at exactly 1 (no localization). Seen on a Brugge run with a variable larger than the field's grid (139 × 48 × 9 = 60,048 cells) declared with that grid: 83% of its rows had taper 1. APEX tapers every row of every variable.
- `GIESMixIn.calc_analysis` computes a prior data mismatch against `real_obs_data`, and `check_convergence` passes `pred_data` with `ne + 1` columns to `calc_objectivefun`, which silently drops the mean-model column by slicing to `pert_obs.shape[1]`.
- `_ext_state` computes a truncated SVD of the scaled prior (`self.Am`) that the RLM-MAC update never uses.
- **Stale forecasts after a rejection.** Nothing restores `pred_data` after a rejected trial, so the next `calc_analysis` pairs the anomalies of `current_state` (the accepted iterate) with the rejected trial's forecasts (`gies_base.py:83, 113`). APEX's `GIES` always proposes from the accepted iterate and its own forecasts.

**SimulatorWrap defects in its geophysics (not reproduced):**
- **G1: `pp_func` accepts only two of its four names.** `pp_func` is looked up by name in `pylops.avo.avo` and called as `f(vp1, vs1, rho1, vp2, vs2, rho2, angle)`. PyLops' `akirichards` and `fatti` are coefficient functions `f(theta, vsvp, n)`, so a configuration naming them fails with a `TypeError`. `zoeppritz_pp` takes scalars only, and fails on the arrays the reference passes. In practice only `approx_zoeppritz_pp` works. APEX's models all take the elastic arrays.
- **G2: evanescent waves.** Past a critical angle, the reference returns NaN from PyLops' `arcsin`, and the NaN propagates into the traces. Every APEX model refuses it (`EvanescentWaveError`, naming the interface, the angle and the wave), and the member fails.
- **G7: every angle gets the last angle's traces.** In `_calc_avo_props_active_cells`, `avo_data = trace_interp` at the first angle binds the buffer that the next angle's loop overwrites in place. So with two angles, `np.stack((avo_data, trace_interp))` holds the second angle twice. With three or more, `trace_interp[:, :, :, np.newaxis]` on a 2-D array raises an `IndexError`. 3dBox's angles 10° and 20° therefore both carry the 20° traces. The `avo_traces` case confirms it, and the reference is generated one angle per call. APEX computes each angle on its own.
- **G3: water's modulus from the mixture's density.** `softsandrp._phaseprops_Smeaheia` takes the pore fluid's density (all phases mixed) as water's, in `K_w = ρ v_w²`. With gas present this underestimates the brine's modulus by the density ratio. APEX uses each phase's own density from the simulator. `test_softsandrp_water_defects_are_pinned` pins it.
- **G4: brine density in mixed units.** Batzle & Wang's salinity term (eq. 27b, g/cm³) is added to a density in kg/m³, so it is 1000 times too small. APEX takes the brine's density from the simulator (whose PVT already holds the salinity), and uses only Batzle & Wang's brine velocity (eq. 29). Pinned by the same test.
- **G5: oil's modulus in Pa.** The oil branch returns `ρ v²` without the `1e-6` the other phases have, so an oil phase's modulus is a million times too stiff. (It also takes the mixture's density as the oil's reference density, as G3 does for water.) APEX returns MPa internally, from the oil's own density.
- **G6: Brie's liquid.** `_fluidprops_Brie` keeps the modulus and saturation of the *last* liquid phase listed (oil or water), so with oil, water and gas the liquid's saturation omits one liquid. It fails with an `UnboundLocalError` when there is no gas, or no liquid. APEX's liquid is the Wood average of oil and water, by their shares of the liquid. Without gas, the fluid is that liquid.
- **G8: no densities, another fluid model.** Without densities, `softsandrp.calc_props` computes Brie's fluid and then overwrites it with `_fluidprops_Wood`, which is `standardrp`'s linear fits at 100 °C. APEX's `soft_sand` requires the densities, so this path does not exist.
- **G9: pressures in the deck's unit.** `flow_rock.calc_pem` passes the run's `PRESSURE` to the PEM in the deck's unit times `press_conv` (default 1), and compares it with the overburden file's values. `standardrp`'s fits take MPa. So a METRIC deck without `press_conv = 0.1` gives bar where the model reads MPa, and its fluids and effective pressure are those of a tenth of the true pressures. The 3dBox AVO case's PET set-up does this. APEX reads the units from INTEHEAD and converts them, and `apex pet-import` gives the overburden file the unit PET's pressures are in, with a note.
- **G10: no AVO without a baseline.** `get_avo_result` puts `base_time` into the first vintage's saved results, but sets it only when `pem` has a `baseline`. Without one, it fails with a `NameError` there. So every PET AVO case that runs has a baseline, and its data are differences from it. `apex pet-import` imports a fixed baseline as `four_d = "differences"`.
- **G11: the region of interest's completions.** The default region (`roi_mode = "ellipse"`) surrounds the wells' completions, which `_load_completion_ij` reads from the rendered deck's own lines only. A schedule in an included file, as in 3dBox, gives no completions. With fewer than two, the region surrounds every active column instead, so 3dBox keeps them all. The completions' columns also depend on the grid's orientation: SimulatorWrap guesses from the column centres' median steps whether x runs along I, and if not, it seeds each completion (I, J) at the column (J, I). `apex pet-import` reproduces both, with the centres in float32 as PET reads them. APEX's own `region = { shape = "ellipse" }` reads the includes and the completions' own columns.
- **G12: the displacement's integral is cut short.** `compute_deformation_transfer` integrates Geertsma's Hankel integrand with `quad` from 0 to λ_max = 15/max ρ (km⁻¹), the largest horizontal distance among the stations it is given for a cell. With the default `receiver_trunc_factor` of 3, those stations reach 3 depths, and the integral loses up to 2.5 % of a cell's largest subsidence. The truncated integral reproduces the reference exactly (case `seafloor_geertsma`), so the cut-off is the whole difference. APEX evaluates the integral in closed form.
- **G13: the sea surface as the free surface.** The displacement model puts the elastic half-space's free surface at z = 0 and seabed stations inside the rock at the water depth. Water carries no shear, so the seabed is the free surface. With a cell at 2000 m, the reference's subsidence directly above it is 0.93 of the seabed-surface value under 100 m of water, 0.79 under 300 m and 0.46 under 1000 m. APEX puts each station on the free surface by default (`free_surface = "stations"`); `"datum"` is the reference's.
- **G14: a larger truncation only lowers λ_max.** `_build_disp_kernel` passes the stations within `receiver_trunc_factor` depths, but `compute_deformation_transfer` zeroes beyond 3 depths regardless. A factor above 3 keeps no more stations: it only lowers λ_max, and so widens G12 (15 % with stations to 6 depths).
- **G15: the `fast` Geertsma mode.** `geertsma_mode = "fast"` uses `2 Δz/R³` (km⁻², times 1e-6) where the integral at the surface gives `(1 − ν)/π · Δz/R³` per unit ΔV: about 8.4 times larger at ν = 0.25. It also measures depth from the station (|z_cell − z_station|), unlike the `integral` mode's sea-level free surface (G13). It is not ported.
- **G16: the rigid basement cannot run.** `compute_deformation_transfer`'s `System_3_vertical` evaluates `j0(lambda_grid * rho)` for a 500-point λ grid and the stations' distances, which broadcasts only with one station or 500, and then indexes the result as `J0_rho[:, i]`, a 2-D index into a 1-D array: it raises for any station list. It is never reached anyway: `map_z_response` lowercases `model` before `_build_disp_kernel` compares it with `'van_Opstal'`, so a `van_Opstal` configuration (any model, in fact) computes Geertsma's integral, with its `geertsma_mode` and truncation, and leaves `z_base` unused. Its equations are Tempone et al. (2010)'s, transcribed correctly; APEX implements them from the paper. Were it to run, it would also zero stations beyond 3 depths, integrate with `trapz` on 500 points to λ_max = 30/max ρ (too coarse for distant stations), put the free surface at sea level (G13) and return cm. A note for porting the horizontal components: the paper's eq. 26 for u₃ has the opposite sign to its eq. 22's convention, so taken literally u₁ + u₂ + u₃ does not vanish at the basement. Its vertical w₃, which APEX uses, is consistent: with eqs. 28–32 both components of the total vanish at z = k, which was checked symbolically.
- **Model limits of `soft_sand` (the reference applies none):**
  - Batzle & Wang's gas modulus fits natural gases, for pseudo-reduced temperatures 1.05–3 and pressures up to 15. CO₂ at the reference's 37 °C has a pseudo-reduced temperature of 0.88. There the modulus is biased (about twice a measured CO₂'s at 20 MPa), and below about 10 °C it turns negative or infinite. APEX refuses such cells unless `extrapolate_gas_correlation` is set, and always refuses a non-positive or infinite gas modulus.
  - For CO₂, APEX's default is Span & Wagner's equation of state (`gas_model = "span_wagner"`, through CoolProp, the `co2` extra), at the simulator's CO₂ density: 2.6 to 6 times softer than the correlation at storage conditions, so results differ from the reference by design. Reproducing it needs `gas_model = "batzle_wang"` with `extrapolate_gas_correlation = true`, which `apex pet-import` writes for `softsandrp` cases, with a note; a configuration that sets only `extrapolate_gas_correlation = true` keeps the correlation too.
  - The dead-oil velocity takes the oil's density at standard conditions (`oil_reference_density`). Without it, the in-situ density stands in.
  - The water and brine fits hold for 0–100 °C and up to 100 MPa.
- **Not reproduced, both models:** the reference computes on outside the models' validity, where APEX refuses with the cell (`PetroElasticError`): a non-positive porosity, a negative clay volume (standard), saturations outside [0, 1] or not summing to 1, and a non-positive dry or saturated modulus, which the reference's `abs(K)` hides. Above φc both models compute as the reference does: `standard` extrapolates its interpolation (φ/φc > 1) up to the clay limit (φ ≈ 0.443), and `soft_sand` caps φ/φc at `porosity_ratio_cap` (0.9), which holds up to φ < 1. Without the cap, `soft_sand` refuses φ ≥ φc. The effective pressure is `max(P_ov − P, 0.01 MPa)`. The reference replaces only negative values, and divides by zero at exactly 0. The two differ only for effective pressures between 0 and 0.01 MPa.

**Not reproduced, the simulator:**
- **Saturations:** the reference clips every saturation to [0, 1]. APEX clips only values within 3e-2 of [0, 1] (a simulator's round-off or overshoot: OPM Flow wrote −4.8e-5 in a 3dBox member, and a derived oil saturation of up to 1.009, and with porosity uncertain 1.021, in one cell of 3dBox members), renormalising a sum within 3e-2 of 1, logs a warning when a value moved by more than 1e-4, and fails the member beyond that.
- **Restarts and units:** APEX reads unified or separate restarts and refuses a missing date with its cause (the reference reads only separate `.X` files and asserts), and takes the units and phases from INTEHEAD. The reference converts pressures only by `press_conv` (G9) and takes the phases from its `pem` configuration's `phases`.
- **NTG** is not read: neither ported model uses it, and the reference passes it on unused.
- **Differences from the previous vintage** (`baseline_mode = "rolling"`) are ported for AVO data: the first vintage minus the baseline, each later one minus the vintage before it, with the vintages listed in increasing order. The import keeps every vintage of the reference's list, also those without data, because the reference's rolling reference moves on at each one. Gravity's and displacement's rolling mode is refused on import: a rolling difference of them is the difference of two fixed ones.
- **Gravity and displacement cells:** the cells are the configured grid's active cells, each centred at the mean of its eight corners (the reference interpolates x and y along the cell's mean pillar at its mean depth, the same for vertical pillars). Every active cell counts: the reference's aquifer filter (`filter_rporv`, which drops the cells above RPORV's 90th percentile in a member it judges to have an aquifer) is not ported.
- **The displacement's volume change:** `c_m V ΔP` takes the bulk volume by default (Geertsma's nucleus of strain; non-net rock included); the reference's baseline pore volume is `volume = "pore"`. Gravity and displacement are always differences from a fixed baseline.
- **Stations' frame and units:** the stations are in the grid's own frame (before MAPAXES), as the reference's, and in m. `apex pet-import` writes the reference's own stations, computed as it computes them in the grid's unit (APEX's regular stations, the same algorithm in m, can round a station count otherwise on a FEET grid or near an integral span). Both assume free-air corrected gravity data and leave out the rock's mass change from compaction.

**bruges defect (not a reference of APEX's, found by the independent tests):**
- **B1: Hashin-Shtrikman shear bounds.** bruges 0.5.4's `rockphysics.bounds.hashin_shtrikman(..., modulus="shear")` evaluates `bound(f, k, z)` with the *bulk* moduli in place of the shear moduli. Its shear bounds are therefore wrong. Its bulk bounds are right and match APEX's. APEX's shear bounds match Berryman's (1995) form with the shear moduli. The test pins bruges' defect by reproducing it with the bulk moduli.
